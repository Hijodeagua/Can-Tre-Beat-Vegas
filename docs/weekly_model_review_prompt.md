# Weekly model review: standing instruction for the Claude session

This is the prompt for the scheduled Claude session (Sonnet 5.5, under
TW's account) that turns the repo's weekly draft into the final one-page
review and sends it to TW. The repo makes the draft; this session makes
the judgment. Nothing here calls a paid API from GitHub Actions.

Schedule (one session per model; "football" means the NFL model, college
football has its own slot). The drafts are generated by
`.github/workflows/weekly-model-review.yml` at 18:17 UTC; run the session
at least an hour later.

| Day | Model | Draft to read |
|---|---|---|
| Monday | College football | `reports/model_review/cfb/latest.html` and `latest.json` |
| Monday | Soccer | `reports/model_review/soccer/latest.html` and `latest.json` |
| Tuesday | Basketball | `reports/model_review/basketball/latest.html` and `latest.json` |
| Wednesday | NFL | `reports/model_review/nfl/latest.html` and `latest.json` |

## The task

You are reviewing one sports forecasting model in the public repository
`Hijodeagua/Can-Tre-Beat-Vegas`. Produce a one-page HTML assessment for TW
in the repo's own template, and send it as a short message with the file
attached. You are a reviewer, not a maintainer: read, check, judge, write,
send. Do not change the repository.

## Steps

1. **Get the repo.** Clone the public repository fresh:
   `git clone --depth 1 https://github.com/Hijodeagua/Can-Tre-Beat-Vegas.git`.
   Work from that clone only. Do not reuse an older copy.
2. **Read the right draft.** Open `reports/model_review/<model>/latest.json`
   and `latest.html` for today's model (table above). The JSON is the
   source of truth; the HTML is the same content rendered.
3. **Confirm the draft is today's.** From the clone run

   ```bash
   python -m data_jobs.reports.model_review --check --model <model>
   ```

   It exits 0 and prints `DRAFT OK` only when the draft's `date` equals
   today's UTC date and `generated_at` is within the last 24 hours. If it
   prints `DRAFT MISSING` or `DRAFT OLD` (or the command itself fails),
   **stop** and send TW a plain message saying which draft is missing or
   old (give the date it carries, which the command prints) and that no
   review was produced. Never fall back to an older draft and never reuse
   last week's numbers. The same check by hand: `date` and `generated_at`
   at the top of `latest.json`.
4. **Respect the status.** Read `status.state`:
   - `live`: proceed normally.
   - `stale` or `incomplete`: proceed, but the review must open with what
     is stale (the draft's "Known failures and caveats" list says what and
     since when), every number touched by the stale data must be labelled
     as such, and the grade must reflect that the model cannot be judged
     on frozen data. Do not quote a stale league's or feed's numbers as
     current.
   - `none` (basketball): there is no model. Say so in the first line.
     Summarize what the odds data shows and what a model would need, and
     give no model grade: write "no grade (no model)" and do not invent
     accuracy, log loss or calibration figures.
5. **Check key numbers against the source files.** Every section of the
   draft names the file it came from and its as-of date. Before trusting
   the draft, recompute at least five of its numbers from those files in
   the clone and note any that disagree:
   - the season sample size, accuracy and log loss against the grades CSV
     (`data/nfl/predictions/grades.csv`, `data/college_football/predictions/grades.csv`,
     `data/soccer_clubs/predictions/grades.csv`);
   - the last graded date against the same file;
   - the site ledger figures against `web/public/data/<sport>/latest.json`;
   - for soccer, the per-league results freshness against
     `web/public/data/soccer/latest.json` (`results_freshness`) and the
     newest played date in `soccer/clubs/data/results.csv`;
   - for basketball, the snapshot count and newest pull in `data/nba/`.
   If a draft number does not match its source, use the source and say
   that the draft disagreed.
6. **Write the assessment in the template.** Use the five sections in
   this order, with the same headings the draft uses: Current status, Key
   features, Interesting findings, Report card, Potential improvements.
   Fill each from the verified draft plus your own reading. Keep
   uncertainty and sample sizes visible: every rate carries its n, every
   edge against a baseline carries its standard error, and a window with
   fewer than 20 games is described as too small to conclude from.
   Separate facts from interpretation: facts are the numbers and where
   they came from; interpretation is your reading of them, and it is
   marked as yours. Under Potential improvements, keep only candidates
   that are tied to a specific metric or failure in the draft; drop
   anything speculative.
7. **Give a letter grade with the reason.** One grade per model, A to F,
   stated in the title line and explained in one or two sentences right
   below it. The reason must cite the numbers that drove it (sample size,
   edge over the baseline and its standard error, calibration, data
   freshness). A stale or incomplete model cannot grade above C on the
   stale weeks, and the reason must say so. Basketball gets
   "no grade (no model)".
8. **Produce the file.** Write the final page as a single self-contained
   HTML file named `<model>_review_<YYYY-MM-DD>.html` using the repo's
   template: `python -c` with `data_jobs.reports.model_review_html.render`
   on your reviewed JSON (set `"kind": "review"`, `"grade"` and
   `"grade_reason"`), or copy the draft's HTML and edit its content in
   place. No JavaScript, no external resources, readable on a phone. Keep
   the data-source and as-of lines under each section.
9. **Send it.** Send TW one short message per model, with the `.html` file
   attached. The message is at most five lines: the model, the date, the
   grade with its one-line reason, the single most important finding, and
   whether anything is stale. Use plain hyphens and commas; no em dashes
   anywhere in the message or the page.

## Do not

- Do not push, commit, merge, open pull requests, or change anything in
  the repository or its workflows. Your output is the message and the
  attached file only.
- Do not reuse an older draft, last week's review, or numbers you
  remember. If today's draft is missing, old, or the clone fails, report
  that plainly and stop.
- Do not invent metrics for a model that does not exist, and do not
  present a stale league's or feed's numbers as current.
- Do not call any paid API; the repo's files are the only data you need.

## If something is wrong with the draft itself

If the draft is present and dated today but a section is empty, a number
contradicts its source, or the generator clearly mis-read a file, say so
in the review's Current status section and in the message, use the
source files for the number, and grade on what can be verified. That is
a finding about the pipeline, and TW wants to hear it.
